# SigmaScope / DeltaScope security-service boundary

SigmaScope is the deterministic production static scanner. It may fetch public plugin artifacts and source material under strict limits, but it never loads or executes the scanned plugin. Candidate Evidence v2 is staged, validated, independently audited, and published fail-closed.

DeltaScope is a developer-only consumer of already-generated evidence. It is read-only by design and must not publish catalog state, Definitions, scanner queues, or Security Evidence v2.

DeltaScope 2.14 browser support follows the published evidence contracts rather than maintaining a competing security model. It can browse lifecycle history, artifact-analysis manifests and their declared datasets, queue/revision state, artifact/manifest/source attribution evidence, endpoint/component summaries, native relationships and secondary-engine evidence. Online browsing remains lazy for large immutable forensic shards. DeltaScope labels endpoint/native/YARA/ClamAV material according to SigmaScope semantics (static/supplemental evidence, not runtime intent or an alternate verdict) and never mutates the evidence it displays.

A SigmaScope implementation/rule change changes the frozen worker/scanner revision on `catalog-data`; it does **not** require an Omega C# version bump. A client bump is needed only when the client-side contract or presentation changes.

## Evidence lifecycle and queue boundary

SigmaScope 2.12 treats variant state as evidence rather than as a reason to erase evidence. Active catalog variants remain the only entries in `currentVariants` and the only normal scan candidates. When a variant becomes inactive or disappears, its current descriptor is converted into a terminal `retired` snapshot with `rescanEligible = false`; its immutable artifact analysis remains referenced and validated. If the same active variant ID later changes artifact identity, the prior artifact descriptor is archived as a `superseded` historical snapshot. Mutable derived/source projection data is not retained in terminal snapshots, and source-only rescans never create an artificial superseded artifact.

The queue is event-driven. Every reason has a contract declaring its work type (`artifact`, `source`, or `advisory`), invalidated evidence layer and event identity. Artifact URL/version or artifact-analysis semantic changes may request artifact work; source-candidate/observation/analysis events request source work; advisory changes request advisory projection only. This boundary is fail-closed and intentionally prevents broad `changed` reasons from accidentally escalating work. Retired variants are never reintroduced as queue candidates merely because historical evidence exists.

## Native binary intelligence

SigmaScope 2.12 adds a bounded, non-executing binary classifier for PE, ELF and Mach-O content. PE parsing identifies machine architecture, 32/64-bit form, executable/library role, managed-vs-native status, subsystem, bounded section metadata and bounded import tables. Native PE library/function imports are projected into SigmaScope's existing static rule and permission evidence, allowing exact APIs to strengthen capability findings without executing or dynamically loading the plugin.

The base artifact classifier still records only shallow ELF/Mach-O identity so normal scanning remains cheap. A separate brokered native-structure collector now deepens retained native evidence without changing artifact-analysis semantics: ELF observations include dynamic dependencies, interpreter, RPATH/RUNPATH, PIE/RELRO/bind-now/executable-stack state and bounded symbols; Mach-O observations include dylib/rpath/load-command structure, slices, segment protections and code-signature presence. Malformed recognized binaries fail closed and plugin binaries are never executed.

Binary-classification contract v2 additionally records PE loader mitigations, entry/image metadata, section permissions and bounded entropy, plus certificate-table presence. Certificate-table presence remains explicitly `verified = false` in the static classifier; platform Authenticode validation is performed separately by the brokered Windows `binarySignatureTrust` collector. Writable+executable native PE sections become bounded caution evidence. Entropy is retained only as context because packed/compressed resources are not themselves malicious.

## Endpoint intelligence

SigmaScope 2.13 uses `omega.sigmascope.endpoint-evidence.v2` to keep network capability separate from destination evidence. Static HTTP(S) literals record an origin type (`artifact-config`, `source-code`, `artifact-text`, `managed-metadata-string` or low-confidence `artifact-binary-string`), confidence, classification and whether the literal is eligible to count as concrete destination evidence. Source/repository references, Discord/community navigation, Lodestone links and certificate/revocation/timestamp infrastructure remain useful forensic literals but are not presented as network destinations.

Endpoint persistence is secret-conscious: credentials, query strings and fragments are removed; Discord webhook tokens and long secret-like path components are redacted. The endpoint summary is bounded and derived. It may say that network capability exists while destinations remain undetermined; that state is preferable to inventing intent from strings. No endpoint classifier performs live DNS, reputation or connectivity checks in the worker.

## Dependency/component presentation boundary

The normalized dependency tables remain authoritative for exact rows, versions, advisory matching, IPC provider resolution, source/artifact comparison and drift. `omega.sigmascope.component-summary.v1` is only a compact derived projection for evidence/client presentation. It keeps NuGet, managed assemblies, native libraries, plugins and IPC relationships separate. Native relationships distinguish exact bundled-library matches, known Windows platform libraries and unresolved/runtime-resolved libraries. A compiled IL call site that directly targets a P/Invoke mapping raises static relationship confidence but never proves that runtime control flow reaches the call.

## Secondary security engines

SigmaScope keeps YARA and ClamAV as **secondary evidence feeds**, never an alternate verdict system. Their matches, availability, engine identity and definition revisions are retained as evidence, while SigmaScope's own artifact/capability findings, severity model and source review coverage remain authoritative.

### ClamAV

Large official ClamAV databases no longer need to live in `catalog-data`. At the daily Definitions boundary the workflow may run FreshClam, collect the resulting CVD/CLD database files, and package them into a deterministic content-addressed ZIP asset on the dedicated `sigmascope-definitions` release. Frozen Definitions record the asset URL, SHA-256, exact byte count, each database hash/size, and the exact `clamscan` executable SHA-256/size/version observed at the same boundary.

Continuous workers **never run FreshClam**. They download only the exact frozen asset, enforce the frozen total byte count, verify the asset SHA-256, allow only the declared archive members, verify every extracted database, and then verify the local `clamscan` executable identity before scanning. A download/materialization failure or executable mismatch leaves ClamAV unavailable for that scan; it does not fall back to system databases or mutable live definitions and it does not block SigmaScope's primary static analysis.

If FreshClam cannot produce a new database at the daily boundary, the catalog workflow attempts to retain the previous frozen content-addressed ClamAV descriptor. If no prior frozen descriptor exists, ClamAV remains disabled rather than inventing an unfrozen input.

### YARA

SigmaScope 2.14 enables the first reviewed production YARA set. Rules remain small enough to live inside frozen Definitions and are governed by `omega.sigmascope.yara-policy.v2`. Every rule file has a same-name `omega.sigmascope.yara-rule-metadata.v2` sidecar containing exact rule names, enabled state, provenance, license, reviewer, review timestamp, **SHA-256 of the exact reviewed rule bytes**, rule class, confidence, false-positive expectation, scope and review notes. The Definitions build fails closed if the sidecar hash differs, if declarations differ from metadata, if names collide across files, or if an enabled file does not compile with the installed YARA executable. Enabled rules also require a frozen executable identity.

The initial Omega Core set contains 14 first-party compound rules across four files. High-signal classes include credential/token access plus exfiltration, classic/NtCreateThreadEx process injection, encoded PowerShell download/execute, Defender tamper commands, base64 PE loading, AMSI memory patching, and Run-key/scheduled-task/service persistence. Anti-debug/anti-VM clusters are explicitly anomaly-class evidence. Broad individual strings such as `HttpClient`, `Process.Start`, P/Invoke, Discord URLs or obfuscation are intentionally insufficient to match.

For ZIP artifacts, YARA no longer sees only the outer container. SigmaScope materializes a bounded generated view of code/config/payload-like members: at most 256 members, 16 MiB each and 64 MiB total, with encrypted/unsafe/suspicious-ratio members rejected and large media/font resources skipped. The original member path is retained only as evidence metadata; it is never used as an extraction path. A YARA match can therefore say which archive member matched, including that member's SHA-256 and byte count. `omega.sigmascope.yara-scan-scope.v1` records target counts, bytes, truncation and skip reasons.

Third-party packs are never imported automatically. `security-definitions/yara/UPSTREAM_REVIEW_QUEUE.md` identifies candidate upstreams such as YARA Forge, signature-base and embee-research for **rule-by-rule** review. Any accepted rule must retain exact upstream provenance/license and pass the same local review/hash contract.

### Shared invariants

Secondary engines remain bound to the exact downloaded artifact SHA-256. ClamAV receives the exact package container; YARA receives that container plus the bounded member view described above. Adapters do not use a shell, do not update signatures, and use bounded execution time/output. Secondary definition, rule-policy, member-scan or executable-identity changes remain bound into `artifactAnalysisRevision`, so stale artifact evidence cannot be silently reused. Historical secondary contract-v2 evidence is preserved as v2; source-only reuse cannot falsely upgrade it to v3. Failing open to live `freshclam`, system databases, unreviewed YARA rules or unpinned enabled engine executables is not acceptable.

## SRL cutover-readiness gate

`tools/security/srl_cutover_readiness.py` is the post-Phase-11 operational audit gate for the first migrated SRL path. It verifies the exact frozen Daily Definitions snapshot plus intrinsic Security Evidence v2, loads only the frozen reviewed SRL ruleset, and combines legacy-baseline replay with retained-observation rule-only reprojection across every current variant. A full-corpus report is mechanically ready only when every current variant is checked, all required retained observations are compatible, hard-coded-vs-SRL outputs match, projection replay has no audit failures, and replay/reprojection classifications agree.

The gate is intentionally **not an activation tool**. Even a completely green report emits `ready-for-human-review` with `manualApprovalRequired=true`, `activationAuthorized=false`, `hardCodedBaselineRemovalAuthorized=false`, `productionWriteBack=false`, and `queueMutationAuthorized=false`. Missing collections produce exact targeted re-analysis requests; filtered/limited runs are diagnostic-only and cannot pass the full-corpus gate. `.github/workflows/srl-cutover-readiness.yml` runs the audit read-only against `catalog-data` + `security-evidence-v2` and uploads only a report artifact.

## DeltaScope / TONI boundary

TONI is a deterministic presentation layer inside DeltaScope only. It may summarize counts and already-published evidence for the operator, but it is not permitted to scan artifacts, change SigmaScope severity/coverage, alter queue state, write Evidence-v2, or participate in publication decisions. The browser remains read-only.


## DeltaScope researcher boundary

DeltaScope 3.7 is a developer-only, read-only security-information workbench over published evidence. Its triage priority/signals are deterministic presentation hints over existing SigmaScope evidence and have **no authority** over scanner severity, coverage, queueing, Definitions, Evidence-v2 publication or Omega client decisions. Online snapshot-race recovery refreshes the published atomic root/index and retries strict SHA-verified reads; it never accepts mismatched bytes.

### Phase 10 rule-only reprojection + Phase 11 workbench shell

Phase 10 evaluates frozen reviewed SRL against retained legal observations without using legacy findings as evaluator inputs. Compatible variants receive deterministic `omega.sigmascope.srl-rule-projection.v1` projections; variants missing a required complete collection receive precise targeted re-analysis reasons. The scan queue carries `srlRuleSetRevision` separately from the hard-coded scanner `ruleSetRevision`. Evidence-v2 can carry a hash/size/schema-verified `rule-projections/` sidecar, but intrinsic validation requires all production/write-back/queue-mutation authority flags to remain false and rejects stale orphan projection files.

Phase 11 completes DeltaScope 3.7 as a read-only investigator console with **Dashboard, Incidents, Events, Intelligence, Assets, Rules, Reports, System**. Slice 2 formalizes the first navigation objects as `omega.deltascope.incident-projection.v1`, `omega.deltascope.event-projection.v1`, and `omega.deltascope.intelligence-projection.v1` under `omega.deltascope.security-workbench.v1`; IDs and the overall projection revision are deterministic, and every object declares `readOnly=true` / `mutationAuthority=none`. Incidents/events/intelligence are derived navigation over evidence, not mutable case-management records. Assets remains the plugin-centric evidence drill-down and Rules contains Rule Lab scratch work. DeltaScope has no direct rule activation, incident mutation, severity/evidence editing, queue mutation, Definitions save, or production publication path. Proposed changes leave the workbench and enter GitHub's permission gate, CI, review and normal PR flow. Phase-11 slice 3 adds `omega.deltascope.incident-case-projection.v1` and `omega.deltascope.security-timeline.v1`: selected incidents/events lazily compose current finding projections, retained observation rows, advisory enrichment, and the Phase-10 non-authoritative SRL projection/reanalysis relationship. Observation previews are bounded, identities are deterministic, and the case/timeline objects remain `readOnly=true` / `mutationAuthority=none`. Slices 4–5 add `omega.security-evidence.workbench-relationships.v1`, a bounded/hash-verified navigation index for endpoint↔variant, component↔variant and advisory↔affected-variant relationships, plus deterministic DeltaScope Intelligence catalog/pivot and Asset relationship projections. The index is explicitly `policyInput=false`; it is not evidence for SRL or a production-policy input. Older Evidence-v2 snapshots remain compatible and simply lack ecosystem relationship pivots. Slices 6–7 add a hash-pinned `omega.security-evidence.definition-provenance.v1` sidecar derived only from the exact verified frozen Daily Definitions root, plus deterministic `omega.deltascope.active-rule-catalog.v1`, `omega.deltascope.report-catalog.v1` and `omega.deltascope.system-status.v1` projections. Active Rules shows frozen pack/rule revisions, review/provenance metadata and fixtures; Reports shows coverage/reprojection/queue health; System shows revision lineage and production/read-only safety gates. The provenance sidecar is `readOnly=true`, `mutationAuthority=none`, `policyInput=false`, and a provenance-only change forces Evidence-v2 publication so DeltaScope cannot retain stale active-rule metadata. Slice 8 completes the Rule Lab handoff with `Propose on GitHub`: local candidate/positive/negative fixture validation is followed only by a bounded query-prefilled normal GitHub Issue Form. The operator submits in GitHub; DeltaScope performs no issue API write and `/api/rule-lab/promote` remains absent.



### Coverage-first queue / DeltaScope coverage visibility

SigmaScope prioritizes never-scanned active variants before revisiting variants that already have published evidence. DeltaScope surfaces this as `Never scanned` coverage and makes `SOURCE CODE` versus `ARTIFACT ONLY` explicit; source availability is not the same thing as source→artifact verification. Online Evidence-v2 cache filenames are short content-derived keys to remain safe on long Windows cache prefixes.

## Capability registry / developer declaration / future rule boundary

The unreleased SigmaScope 2.15 development line implements the shared capability vocabulary, `.omega/plugin.yaml` ingestion, deterministic behavior-consistency projection, and Phase-4 observation/projection replay boundary. Production 2.14 scans/catalog/evidence remain untouched while this migration line is developed. `security-definitions/capabilities/registry.json` is the canonical descriptive capability registry used by profile validation and DeltaScope today and intended for SRL/Omega UI later. Registry entries can name/describe a capability but do not carry a malware verdict.

Attributed source may provide `.omega/plugin.yaml`. It is developer-provided explanation, not scanner authority. The parser is bounded, SafeLoader-based, rejects YAML anchors/aliases/tags/merge keys/duplicate keys and rejects authority-like fields such as safety/trust/verdict/severity/suppression/source-verification claims. Invalid enrichment is fail-soft. The normalized profile is retained in source analysis/Evidence-v2 and projected for UI, but it cannot change SigmaScope findings, secondary security evidence or provenance.

The developer profile may declare canonical capabilities as expected or explicitly not expected and explain services/native components/IPC. `omega.sigmascope.behavior-consistency.v1` now compares those claims with independent canonical capability and concrete endpoint observations for presentation/research. It distinguishes no-profile from undeclared, prevents `.omega` URLs from proving themselves, and never changes native findings/severity. Absence of an observation is still not proof of absence unless compatible coverage supports that conclusion.

SigmaScope Definition Packs now use a bounded, non-executable Sigma-inspired YAML DSL over typed normalized observations/facts on the unreleased 2.15 line. They complement rather than replace YARA, ClamAV, OSV or future integrity/signing engines. DeltaScope now exposes `capabilities`, `observation-schema`, and `rule-schema` authoring references plus the Phase-8 visual Rule Lab. Rule Lab imports/edits inert candidate YAML, compiles with the same SRL engine, dry-runs selected retained Evidence-v2, exposes selector traces and baseline diffs, replays bounded selected/corpus sets, creates/tests fixtures, and exports deterministic hash-pinned candidate ZIPs. It has no production write-back endpoint or promotion authority. DeltaScope 3.7 adds a URL-only **Propose on GitHub** handoff: candidate + positive/negative fixtures are validated locally, then GitHub's normal `sigmascope-rule-candidate.yml` Issue Form is opened with canonical field-ID query prefills. DeltaScope never submits the issue or performs a GitHub API write; oversized URLs degrade to bounded metadata/identity prefills plus explicit copy actions. Daily Catalog can now fail-closed compile/freeze reviewed source-controlled packs; Phase-9 authorization-gated GitHub candidate promotion is implemented locally: issue YAML/fixtures are inert bounded data, validation cannot write repository contents, and promotion requires a fresh repository-permission check plus fresh validation before a normal review PR is opened. Full implementation and authoring docs: `docs/ARCHITECTURE-SECURITY-MODEL.md`, `docs/OMEGA-PLUGIN-PROFILE.md`, `docs/BEHAVIOR-CONSISTENCY.md`, `docs/SIGMASCOPE-RULE-LANGUAGE.md`, `docs/DELTASCOPE-RULE-WORKBENCH.md`, `docs/IMPLEMENTATION-PLAN-RULES-PROFILES.md`, `docs/plugin-developers/`, and `docs/rule-authors/`.

### Unreleased 2.15 Phase-4 observation/projection boundary

`omega.sigmascope.observation-contract.v1` gives retained low-level inputs a stable logical collection boundary independent of current conclusions. `omega.sigmascope.projection-contract.v1` identifies the deterministic evaluator/rule context separately from output record digests. Legacy `findings`, `permissions`, `automation`, and presentation `behaviorConsistency` remain readable for parity/research but are not legal recursive future SRL inputs.

New 2.15 Evidence exports report-only observations such as native imports, full endpoint rows, source files, binary classifications, developer profile/provenance, artifact/manifest identity and secondary-security results as first-class analysis datasets. Historical 2.14 variants are adapted at synchronization time from their retained immutable datasets plus compact report without downloading/reopening plugin bytes. If historical compact transport is known to be bounded (notably endpoints), replay audit marks it insufficient for an exact rule and requires targeted re-analysis instead of assuming omitted rows are absent.

The security observation contract uses `observationContractRevision` / `projectionContractRevision`; do not reuse Definitions' existing `sourceObservationRevision`, which is the unrelated source-repository-ref observation identity. A Definitions/rule change alone is never a rescan reason. See `docs/OBSERVATION-PROJECTION-CONTRACT.md`.


### Phase 9 candidate-rule GitHub review boundary

`tools/security/rule_candidate.py` validates the fixed candidate issue fields using the same hardened SRL and Definition Pack compiler. Positive fixtures must collectively exercise every candidate rule; negative fixtures must match none. Existing pack IDs, path-like IDs, duplicate cross-pack rule/fact identities, unsafe YAML constructs and failing fixtures are rejected. Candidate or issue-author identity is never authorization.

`.github/workflows/rule-candidates.yml` is the canonical reusable workflow for the `sigmascope` branch. Its validation job has `contents: read`; the promotion job checks the triggering `github.actor` through GitHub's repository collaborator-permission endpoint before checkout or candidate re-fetch. Only then does it revalidate/materialize a new `reviewed` pack, record the verified reviewer and issue-body SHA-256, push a dedicated branch and open a normal PR. There is no auto-merge and no `pull_request_target`. The default-branch event caller is documented in `docs/workflow-callers/rule-candidates-main.yml`; the exact default-branch Issue Form reference is `docs/workflow-callers/sigmascope-rule-candidate-main.yml`. Production SRL projection remains disabled and a merged pack still requires the separate Daily Definitions freeze.

### SRL v1 local compiler/evaluator boundary

The unreleased 2.15 migration tree implements a deterministic, non-executable SigmaScope Rule Language compiler/evaluator in `tools/security/srl.py`. It may read only registered typed Phase-4 observations and typed facts, never arbitrary files/network/process/SQL/environment state. Observation/classification rules emit facts; correlation rules may consume observations/facts but emit findings only, preventing recursive finding/fact cycles.

DeltaScope can compile/test/evaluate candidate YAML locally, and Definition Pack v1 content can be validated/frozen by Daily Catalog. Phase 7 now has reviewed production-tier packs for the five `staticPatternMatches` primitive fact producers plus `compound.network-execute` and `compound.credential-network`. `rule-parity` proves every legacy primitive literal (canonical and case-perturbed, plus near-miss guards: 59 cases) and all 32 compound input combinations. Daily Definitions fails closed on a partial migration or any drift. `rule-replay --evidence-v2 ...` replays only legal retained observations and uses old findings as comparison baselines only. Production SRL projection is still **disabled**: existing live 2.14 evidence lacks the new complete static-pattern observation contract and is therefore explicitly marked for targeted 2.15 re-analysis instead of being treated as replay-compatible.
